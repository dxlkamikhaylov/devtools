## Code Review Checklist

### Функциональность
- [ ] Код решает поставленную задачу полностью
- [ ] Обработаны граничные случаи (null, пустые данные, экстремальные значения)
- [ ] Обработка ошибок реализована корректно

### Тесты
- [ ] Добавлены тесты для нового функционала
- [ ] Все тесты проходят локально: ./gradlew test
- [ ] Покрыты позитивные и негативные сценарии
- [ ] JaCoCo coverage >= 80% для нового кода

### Читаемость и стиль
- [ ] Имена переменных, методов и классов отражают назначение
- [ ] Нет дублирования кода (DRY)
- [ ] Checkstyle проходит без ошибок: ./gradlew checkstyleMain
- [ ] Нет закомментированного кода или отладочного вывода (System.out.println)

### Документация
- [ ] README обновлён (если добавлена новая функциональность)
- [ ] Публичные методы имеют JavaDoc (если применимо)
- [ ] Runbook обновлён (если изменились команды)

### Производительность и безопасность
- [ ] Нет очевидных проблем производительности
- [ ] Нет хардкода паролей, токенов или конфиденциальных данных

## Примеры Code Review комментариев
**Проблема:** [конкретное описание с указанием строки]
**Почему это важно:** [последствия]
**Предложение:** [как исправить или альтернатива]

### Конструктивные комментарии

#### Пример 1:

> **Проблема:** В файле ProgressDemo.java используются System.out.println для вывода информации (строки 10, 12, 14, 17).
 В рабочем коде (класс MenteProgress) подобный вывод также недопустим.
>
> **Почему это важно:** System.out.println — это отладочный вывод, который засоряет консоль production-окружения,
 не имеет уровней важности, не сохраняется в логах и не может быть отключен без изменения кода.
>
> **Предложение:** Заменить все System.out.println на вызовы логгера SLF4J (log.info(...), log.debug(...)).
 Для демонстрационного класса ProgressDemo вывод можно оставить, но при условии, что он не используется в production-коде.

*Почему это хороший комментарий:* он аргументирован и конструктивен — объясняет суть проблемы и предлагает улучшение.

#### Пример 2:

> **Проблема:** В методе readyForSprint() класса MenteProgress (строка 5) используется число 3 без объяснения его смысла.
>
> **Почему это важно:** Из кода непонятно, что означает это число — минимальное количество часов в неделю? Порог для готовности к спринту?
 Если бизнес-правило изменится, разработчику придётся искать значение по всему проекту.
>
> **Предложение:** Вынести значение в именованную константу: `private static final int MIN_HOURS_FOR_SPRINT = 3;` и использовать её в условии.

*Почему это хороший комментарий:* он построен по шаблону «Проблема → Почему важно → Предложение» — содержит аргументацию и конкретное решение.

### Токсичные комментарии

#### Пример 3:

> «Опять эти System.out.println по всему коду! Ты вообще думаешь, что пишешь? Кто тебя этому учил?»

*Почему это плохой комментарий:* переход на личности («ты вообще думаешь»), сарказм и обесценивание («кто тебя этому учил»),
 нет указания на конкретное место и нет предложения. Вызывает защитную реакцию и демотивирует автора.

#### Пример 4:

> «Это что за магическое число 3? Бред какой-то. Убери эту ерунду, пока я не увидел.»

*Почему это плохой комментарий:* оскорбительная лексика («бред», «ерунда»), угрожающий тон («пока я не увидел»),
 отсутствует объяснение проблемы и конкретное предложение по исправлению.

## Результаты само-ревью DVT-9

### Проблема 1: Магическое число 3 в MenteProgress.java

> **Проблема:** В файле `src/main/java/ru/mentee/power/MenteProgress.java`
> (строка 5) в методе `readyForSprint()` используется литерал `3`.
> Из кода невозможно понять, что это за порог: минимум часов в неделю?
> Количество спринтов? Условие для какого-то статуса?

> **Почему это важно:** Литерал в условии `plannedHoursPerWeek >= 3` не несёт
> смысловой нагрузки. Если бизнес решит изменить порог (например, на 5),
> разработчику придётся искать эту тройку по всему проекту — а она может
> использоваться в нескольких местах (тесты, документация, UI). Это создаёт
> риск рассинхронизации и повышает стоимость поддержки.

> **Предложение:** Вынести литерал в `private static final int`
> константу с говорящим именем:
> `private static final int MIN_HOURS_FOR_SPRINT = 3;`
> После этого условие станет самодокументируемым:
> `return plannedHoursPerWeek >= MIN_HOURS_FOR_SPRINT;`
> При изменении бизнес-правила достаточно поправить одну строку.

### Проблема 2: Отсутствие Javadoc на публичных методах

> **Проблема:** В файле `src/main/java/ru/mentee/power/MenteProgress.java`
> публичные методы `readyForSprint()` (строка 4) и `summary()` (строка 8)
> не имеют Javadoc-комментариев.

> **Почему это важно:** Без документации другим разработчикам (и IDE)
> непонятно назначение методов, их контракт и возвращаемые значения.
> Например, из сигнатуры `readyForSprint()` неясно, при каких условиях
> метод возвращает `true`, а при каких — `false`. Это усложняет
> использование класса и поддержку кода.

> **Предложение:** Добавить Javadoc перед каждым публичным методом
> с описанием назначения и возвращаемого значения. Например, для
> `readyForSprint()` — указать, что метод проверяет готовность менти
> к спринту и возвращает `true`, если запланировано не менее
> `MIN_HOURS_FOR_SPRINT` часов в неделю.

### Проблема 3: Отсутствие валидации входных данных в MenteProgress

> **Проблема:** В файле `src/main/java/ru/mentee/power/MenteProgress.java`
> (строка 11) `record MenteProgress` не проверяет входные данные.
> Можно создать объект с `menteeName = null`, пустой строкой
> или отрицательным `plannedHoursPerWeek`.

> **Почему это важно:** Некорректные данные могут привести к ошибкам
> во время выполнения — например, `NullPointerException` при вызове
> `summary()`, либо к бессмысленному результату `readyForSprint()`
> при отрицательных часах. Лучше валидировать данные на входе,
> чем ловить баги в production.

> **Предложение:** Добавить компактный конструктор с проверкой
> входных данных. Для некорректных значений (`null`, пустая строка,
> отрицательные числа) выбрасывать `IllegalArgumentException`
> с понятным сообщением об ошибке.
